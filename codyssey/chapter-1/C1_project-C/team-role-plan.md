# Project C — 팀 역할 분배 & 킥오프 플랜 (사전 준비용)

> 다음 주 랜덤 팀 편성 전에, 첫 회의에서 바로 꺼내 쓸 역할 분배안. 4명 기준으로 짜고 5명/3명 변형을 함께 담았다.
> 과제 3대 산출물: ①자동화 워크플로우 ②플랫폼별 콘텐츠+노션 ③프롬프트 템플릿(초안→수정→최종). 도구: Make + OpenAI(텍스트·이미지) + Notion.

---

## 1. 왜 이렇게 나누는가 (분배의 원리)

이 과제는 **데이터가 사슬처럼 흐른다**: `주제 입력 → 프롬프트 → Make 조립 → 이미지 → 노션 저장`.
그래서 "각자 다른 플랫폼 하나씩" 식으로 나누면 안 되고(중복·충돌 발생), **파이프라인 단계별로** 나눠야 병렬 작업이 가능하다. 아래 4트랙은 서로 **의존은 있지만 동시에 착수 가능**하도록 설계했다.

---

## 2. 4명 기준 역할 분배 (표준안)

| 트랙 | 역할명 | 담당 산출물 | 핵심 업무 |
|------|--------|------------|-----------|
| **A** | 🔧 워크플로우 아키텍트 | ① 자동화 워크플로우 | Make 시나리오 빌드(트리거→텍스트→이미지→노션 저장), 모듈 연결·매핑, 실행 성공시키기, 구조 스크린샷 |
| **B** | ✍️ 프롬프트 엔지니어 | ③ 프롬프트 템플릿 | 플랫폼별 프롬프트 설계(글자수·해시태그·톤), 실행 결과 보고 **수정 이력(초안→수정→최종)** 기록, 보너스 A/B 톤 변형 프롬프트 |
| **C** | 🎨 콘텐츠·이미지 디렉터 | ② 콘텐츠 결과물 | 이미지 프롬프트 설계·품질 검수, 3개 플랫폼 텍스트 최종 검수(글자수/해시태그 규칙 준수 확인), 보너스 A/B **효과 결론 정리** |
| **D** | 📋 노션·문서 PM | ② 노션 페이지 | 노션 콘텐츠 DB 설계(플랫폼별 구분 저장), 프로젝트 개요·**팀 역할·개인 작업 요약** 작성, 발표/제출 문서 총괄 |

> **누가 뭘 맡든 "과제 목표 3가지"는 전원이 설명할 수 있어야 함**(동료 평가 대비): ①플랫폼별 자동 생성 워크플로우 ②텍스트+이미지 연동 자동화 ③포맷 고려 프롬프트 설계 원리.

## 3. 인원별 변형

### 👥 5명일 때 (+1 트랙 분리)
- **E — QA·발표 담당**: 요구사항 체크리스트 대조(누락 방지), 리허설, 발표 진행. 또는 보너스 A/B 테스트를 C에서 떼어 E 전담.
- 랜덤 팀에서 가장 부담 큰 트랙 A(Make 빌드)에 E를 페어로 붙이는 것도 좋음(빌드 2명·검증 1명).

### 👥 3명일 때 (트랙 병합)
- **A(아키텍트)** 유지 — 기술 핵심이라 단독.
- **B+톤** → 프롬프트+A/B 보너스 묶어 1명.
- **C+D** → 콘텐츠 검수 + 노션·문서 묶어 1명.

### 👥 2명일 때 (미정 대비)
- **1명**: A(Make) + C(이미지)  →  "기술·생성 담당"
- **1명**: B(프롬프트) + D(노션·문서)  →  "설계·정리 담당"

## 4. 킥오프 진행 순서 (첫 회의 30분 + 이후 흐름)

**의존성 때문에 착수 순서가 중요하다.** 아래대로 하면 병목이 안 생긴다.

```
[0] 전원 (첫 회의 30분)
    - 주제 1개 확정  +  노션 DB 스키마 합의(플랫폼/본문/이미지/주제 속성)
    - 역할 배정, 과제 목표 3개 함께 읽기
        ↓
[1] 병렬 착수
    - B: 프롬프트 초안 v1 작성        ─┐
    - C: 이미지 프롬프트 초안         ─┤→ A에게 전달
    - D: 노션 DB 뼈대 + 페이지 개설   ─┘  (스키마 확정)
    - A: Make 트리거+골격 세팅(폼 연결)
        ↓
[2] 통합 (A 주도)
    - A가 B프롬프트·C이미지프롬프트·D스키마를 Make에 조립 → 첫 실행
        ↓
[3] 실행·디버깅
    - 첫 결과 확인 → B가 수정 이력(초안→수정→최종) 기록
    - C가 텍스트/이미지 품질 검수(글자수·해시태그·280자 등)
        ↓
[4] 마무리
    - 보너스 A/B(친근 vs 전문) 실행 → C 결론 정리
    - D가 노션에 최종 정리 + 개인별 작업 요약 취합
    - (5명이면) E 리허설·체크리스트 대조
```

**핵심 병목 주의**: 노션 DB 스키마(D)가 확정돼야 A가 저장 모듈을 매핑할 수 있다 → **스키마 합의를 [0]단계에서 반드시 끝낼 것.**

## 5. 각 요구사항 → 담당 매핑 (누락 방지용)

| 요구사항 | 주담당 | 검증 |
|----------|--------|------|
| 주제 입력·트리거 구현 | A | D |
| 3개 플랫폼 텍스트(특성·톤 반영) | B | C |
| 대표 이미지 생성(SNS 품질) | C | A |
| 노션 플랫폼별 구분 저장 | A+D | D |
| 프롬프트 수정 이력(초안→수정→최종) | B | C |
| 노션: 프로젝트 개요·팀 역할·개인 작업 요약 | D | 전원 |
| 보너스: A/B 톤 테스트 + 결론 | B(생성)+C(결론) | D |

## 6. 내가(사전 준비자) 회의에서 리딩할 포인트

- "역할을 플랫폼별로 쪼개지 말고 **파이프라인 단계별로** 나누자" — 이 한마디가 팀 효율을 가른다.
- 이미 만들어 둔 **프롬프트 템플릿 초안·워크플로우 설계도**를 공유하면 초반 30분을 아낀다. (`prompts/prompt-templates.md`, `workflow/workflow-spec.md`)
- **노션 스키마 합의 먼저** — 안 그러면 Make 저장 단계에서 전원이 대기한다.
